- (note) Inputs: PRD prd-BMad-2026-09-21/prd.md (rich, structured, 17 FRs across 6 groups) + Architecture architecture-BMad-2026-09-21/ARCHITECTURE-SPINE.md (AD-8..AD-12 new, AD-1..AD-7 inherited from the Browser spine). Both fully authored by prior BMad skill runs -- trusting the authored separation, no elicitation needed.
- (capability) CAP-1: Batched dash-one entry. Intent: user working through a baseline sets a shared organization-defined parameter once for the whole cluster of policy/procedure ('dash-one') controls instead of once per control. Success: setting one clustered value writes an independent, individually-overridable decision for every matching control in the baseline (verified against real data: 18 of 20 dash-one controls share an identical 9-parameter shape in Moderate).
- (capability) CAP-2: Individual parameter decision + rationale. Intent: user sets a value for any single parameter (batched or not), records its review status, and (when overriding a default) a written rationale. Success: a parameter's status is one of unreviewed-default/confirmed/overridden; overridden requires a non-empty rationale before the change is accepted.
- (capability) CAP-3: Readiness gate + dashboard. Intent: user sees what fraction of the baseline's parameters are still unreviewed, jumps directly to any outstanding one, and cannot mark the baseline ready until none remain unreviewed. Success: the ready action is blocked while any parameter is unreviewed-default; the dashboard's counts match the underlying decision data exactly.
- (capability) CAP-4: OSCAL export. Intent: user exports all current decisions as a valid OSCAL Profile document, one set-parameter per decision, each carrying its rationale. Success: the exported document validates against the OSCAL 1.2.2 schema via oscal-cli, with one set-parameter per decision (fanned out from any batched cluster, never combined) and rationale preserved in remarks.
- (capability) CAP-5: Local persistence. Intent: decisions survive a page reload/return visit on the same browser. Success: reloading the workspace after closing the tab shows the same decisions as before, with no account or server round-trip involved.
- (constraint) Static-site only, no backend/accounts -- decisions live entirely client-side (AD-1, inherited).
- (constraint) One dedicated workspace page/island owns all decision state; no other page reads or writes it (AD-9). Control detail pages may link in, never edit.
- (constraint) Storage shape: one JSON blob per baseline in localStorage (key odp-decisions:<baseline>), single schemaVersion, one shared read/write module (AD-10). Decision key = controlSlug:paramId. A corrupt/missing blob is treated as empty state, never a crash or a fabricated value.
- (constraint) value is string | string[] -- an array whenever the source parameter's select.howMany is 'one-or-more' (97 real parameters corpus-wide, including one present in every dash-one control). A naive single-string assumption silently drops selections on export and breaks cluster-match comparison (AD-10, AD-11 -- caught in architecture self-review).
- (constraint) Dash-one clustering match rule: paramId after stripping the ^<familyCode>-1_ / ^<familyCode>-01_ prefix, computed at read time only -- never stored as a cluster reference (AD-11). A batched write still lands as N fully independent decisions.
- (constraint) ODP dataset available to the client is generated at build time from the already-committed Content Collection (AD-8) -- never by re-parsing raw OSCAL or extending the ingestion script's scope.
- (constraint) OSCAL export targets oscal-version 1.2.2 (the corpus's own ingested version) -- one set-parameter per decision, values array, rationale in remarks (AD-12). Validity checked manually via oscal-cli during development; no client-side schema validator ships.
- (constraint) V1 scope is the Moderate baseline only; other baselines are not built or tested even though the route/dataset are parameterized for them.
- (decision) Non-goals (from PRD): not multi-user/no accounts/no sync; not an assessment-workflow tool (no SAP/SAR authoring, no POA&M tracking); not a GRC platform or 3PAO tooling replacement; not an SSP narrative generator (FedRAMP 20x deprecates that artifact, mandatory Jan 2027); not an OSCAL-native editor (OSCAL is an export target, not the primary working format -- real-world adoption is still near zero per FedRAMP RFC-0024); not scoped beyond the Moderate baseline for v1.
- (decision) Why (from PRD Vision): FedRAMP Notice 0013 (2026) removed centralized ODP defaults because they'd become unexamined ceilings -- CSPs must now choose and document ~643 parameter values themselves per Moderate baseline, including 18 structurally-identical dash-one policy-control clusters answered one at a time today. The workspace batches the identical clusters, forces a reviewed status + rationale on every value before a baseline can ship, and exports the result as a real OSCAL profile.
- (decision) Success signal: (1) the readiness gate blocks marking a baseline ready while any parameter is unreviewed-default -- demonstrable by attempting the ready action with 1 remaining unreviewed parameter and confirming it's blocked; (2) an exported OSCAL profile passes 'oscal-cli validate' with one set-parameter per decision and rationale present in remarks for every overridden value.
- (constraint) Accessibility (PRD NFR-3): batch-entry, status toggles, dashboard must be keyboard-operable/screen-reader-navigable following the Browser's existing role/aria-expanded/focus-visible patterns.
- (constraint) Browser support (PRD NFR-5): modern evergreen browsers only, no polyfills.
- (constraint) Export-as-backup framing (PRD NFR-1): no auto-backup exists, so export must be presented in the UI as the user's durable copy, not an optional extra.
